# 设计

Rove 是一个 Rust crate。它为一个离散性状矩阵，在 Mk 模型下计算有根二叉树的似然。下面的决定是已经在代码中可见的那些。它们所铺垫的 SIMD 工作已从 [NEON 后端](./kernel#后端)开始，其余部分在[路线图](./roadmap)上。

## 位点模式主序布局

似然内核把时间花在把转移矩阵乘进部分似然上。BEAGLE 的 CPU 内核沿状态向量化，并针对四个状态做了特化，这适合核苷酸。形态学矩阵大多是二态和三态性状，所以这些内核会走带填充的通用路径。

Rove 反过来存放部分似然。对每个速率类别和每个状态，有一段连续的值，每个位点模式一个，填充到八个通道的倍数。内层循环沿模式运行，因此两个状态和六十一个状态的循环形状相同。

`Layout` 描述这种安排：状态数、速率类别数、模式数，以及填充后的步长。`offset(category, state)` 给出一段连续值的起点。

## 面向模型的快速路径

Mk 有闭式解。一条分枝的转移矩阵是 `P(t) = e·I + (1 − e)·π`，其中 `e` 只取决于枝长，`π` 存放状态频率。把它乘进一个向量，每个模式只需 O(k) 而不是 O(k²)。

用 `LikelihoodCore::mk` 构建的 Mk 核心直接使用这一形式。每条分枝按速率类别存放一个距离以及 `e` 和 `1 − e`，而不是一个矩阵；更新子节点时，每个模式只计算一次按频率加权的和，由所有状态共用。矩阵核心保留下来，用于没有这种形式的模型，测试会把两者都与参考实现比较。

在 Apple M4 Max 上，[直接 Mk 对比](https://github.com/getcortexlabs/rove/blob/main/benchmarks/rove/2026-10-28/README.md)在相同的进程中测量了两种核心。对 20 × 50 参考数据做一次完整求值，矩阵核心用时是 Mk 核心的 1.25 倍；二态 90 × 250 矩阵为 1.11 倍；八个状态时为 2.66 倍。两个状态时，两条路径的运算量几乎相同，而 Mk 路径遍历内存的次数更少。

## 始终保留标量参考实现

`reference::Problem` 是 Felsenstein 剪枝算法的朴素递归实现。它故意又慢又简单。等价性测试构建随机树，并把 `LikelihoodCore` 与它比较：用末端节点状态和用末端节点部分似然，有重缩放和无重缩放，相对容差为 1e-9。`variable_log_likelihood` 以同样直接的方式应用 Mkv 校正。

以后加入的每条优化路径都必须通过同样的测试。参考实现会一直保留。

## 双缓冲与重缩放

每个节点拥有两个部分似然缓冲区和两个分枝缓冲区，分枝缓冲区存放转移矩阵或 Mk 距离。在一次提议覆盖某个节点之前，`set_node_partials_for_update` 或 `set_node_matrix_for_update` 会把该节点切换到另一个缓冲区，这样先前的值得以保留。`store` 记录哪些缓冲区是当前的。`restore` 通过交换把那一组带回来，`unstore` 则通过复制。接受一次移动不花任何代价。这正是 MCMC 采样器要低成本地拒绝一次移动所需要的。

使用 `Scaling::Always` 时，每个节点根据每个模式在所有状态和类别中的最大值，选择二次幂进行缩放。缓冲区以整数保存整个子树的指数：本地指数加上两个子节点的总指数。根节点对每个模式只计算一次 `E * ln(2)` 来恢复缩放，无需遍历所有节点。指数随部分似然缓冲区一起恢复。详见[具体约定](./kernel#重缩放)。

## 在同一个核心中计算恒定模式

Mkv 校正需要每个恒定模式在与观测相同的树、速率和缩放下的概率。Rove 把这些模式追加到核心的末端节点输入中，而不是单独计算，因此局部更新、重缩放以及存储/恢复无需改动就能覆盖它们。对于 20 × 50 参考数据，两个额外的模式使填充后的步长从 24 增加到 32，每次节点更新要多处理三分之一的通道。

## 建立在同一组缓冲区之上的采样器

[采样器](./sampler)把树及其参数保存在核心之外。每一步之前，它保存这些值，并记录核心的缓冲区索引。提议之后，它把新树与保存的树进行比较，把每条变化的分枝的新距离写入它的另一个缓冲区，并且只重新计算这些分枝的祖先。被拒绝的一步会把索引换回来。这些提议重现了 BEAST 2 的算子和 Hastings 比，因此与 BEAST 的比较可以使用相同的移动和权重。

参考配置在保存状态中增加 gamma 形状、时钟 sigma 和显式分枝速率。只改变 sigma 不影响似然；sigma 与速率联合移动会更新分枝距离；改变形状会更新整棵树各类别的距离。其提议与 ORC 不同，详见[参考模型指南](./reference-model#提议与输出)。

## 采样器各阶段的耗时

[90 和 500 个分类单元的性能分析](https://github.com/getcortexlabs/rove/blob/main/benchmarks/profile/2026-10-31/README.md)在 Apple M4 Max 上测量了当前采样器。可选的基准测试构建按墙钟时间采样执行阶段，并非原生 CPU 调用栈采样。八组配对运行均重现了普通构建的轨迹数值、树和算子统计。报告保留了插桩与普通构建的耗时比、环境波动及两次重复的结果。默认构建不包含性能采样代码。

使用参考预设时，节点部分似然与重缩放合计占 90 个分类单元观测的约 68%，以及 500 个分类单元观测的约 82%。即使已用二进制指数替代对数，重缩放本身仍占约 22–23%：它仍需缩放部分似然并累加子节点指数。按这些插桩观测比例，即使内核耗时降为零，观测窗口内的加速上限也分别约为 3.14 倍和 5.50 倍，根节点归约、树遍历、提议及输出仍需耗时。这是有条件的上限，并非实际运行的加速承诺。[独立链研究](https://github.com/getcortexlabs/rove/blob/main/benchmarks/convergence/2026-10-31/README.md)另行评估采样质量。

## NEON 优先，AVX2 其次

布局的存在是为了让内层循环可以沿模式方向向量化。在 release 构建中，编译器已经会逐个循环地对可移植代码进行向量化：一次节点更新先把两个累加器清零，把每个状态的贡献加到其中，再把它们与子节点的部分似然组合，之后重缩放还要重新读取结果，找出每个模式的最大值。[NEON 后端](./kernel#后端)则以八个模式为一块，一次遍历完成 Mk 的节点更新，累加和与最大值都保存在寄存器中。对每个模式，它执行相同的运算，顺序也相同，因此除 NaN 的载荷外，逐位重现可移植代码的结果，测试也要求如此。在 Apple M4 Max 上，对参考矩阵做一次完整求值，可移植代码的用时是 NEON 的 1.48 倍（[报告](https://github.com/getcortexlabs/rove/blob/main/benchmarks/neon/2026-10-28/README.md)）。重缩放现在通过整数运算提取二进制指数；NEON 每个寄存器处理两个模式。目前没有 AVX2 路径。

## 单个 crate

Rove 不依赖 BEAST 或 BEAGLE。BEAST 是验证和基准测试的参考。BEAGLE C ABI 和通过 JNI 的 BEAST 2 `LikelihoodCore` 适配器是可能的兼容路径。两者都不是 Rust 核心所必需的，现在也都没有在构建。

## 非目标

在大型核苷酸比对上与 BEAGLE 的 CUDA 后端竞争。那种情况请用 GPU。
