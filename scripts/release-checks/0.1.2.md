## Upgrade exercise

The source copy used build `3` with the same bundle ID, signing identity and
application content as the candidate. It was signed, notarized and stapled
separately; submission `c9600451-ed55-49bf-ac3f-42ca32bc2dbb` was accepted.
Build 3 is a local installer fixture, not a published release or an old-engine
compatibility test. The destination was the exact final build-4 DMG above.

| Check | Result |
| --- | --- |
| Automatic discovery | Found build 4 through the local signed feed; the test made the previous check overdue. |
| Automatic download opt-in | Settings started with downloads off, allowed enabling them, and the opted-in background check downloaded the archive. |
| Skip and manual check | Skipping dismissed the offer. A subsequent manual check offered the same build again. |
| Installation and relaunch | The separate copy advanced from build 3 to 4 and relaunched. Its signature remained valid. |
| Existing data | The original four history entries, history folders and onboarding flag were unchanged after the first upgrade. Beta access remained active. |
| Active analysis | With a 100M-step example run active, requesting installation twice did not stop the calculation. Settings showed the pending update with installation disabled. |
| Explicit later installation | After cancelling only the test analysis at 39,886,848 steps, the installed copy remained at build 3. The Settings button became enabled; clicking it installed build 4 and relaunched. |
| Cleanup | The temporary run was moved out of the user's runs folder, the original four history entries were restored, and test updater preferences and the local server were removed. |

The targeted native suites passed 12 tests covering updater configuration,
signatures and tampering, nested engine activity, installation deferral,
preferences and launch experience. Other engine tools share the activity gate;
their nested-process behavior is covered by unit tests, not a separate manual
tool-installation exercise in this record.
